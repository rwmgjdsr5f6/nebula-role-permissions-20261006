一、公开入口与从命令到 JSON 输出的完整路径
------------------------------------------
唯一公开入口是命令行：

    python -m rbac --db FILE export-rules

参数注册位置：rbac/__main__.py 的 _build_parser() 中
subparsers.add_parser("export-rules", ...)，该子命令不接收任何位置参数。

一次调用从输入到输出严格按以下顺序执行（编排位置：rbac/__main__.py
的 main()）：

1. 参数解析与名称校验的跳过
   argparse 解析 --db 路径与子命令。main() 对 export-rules 取
   raw_names = ()（空元组，源码注释"不接收成员、角色或权限参数，无需
   名称校验"），因此本命令不经过 policy.normalize_name() 的名称规整，
   也不可能触发 invalid_name（退出码 2）分支。
   核对位置：rbac/__main__.py main() 中 `if args.command ==
   "export-rules": raw_names = ()` 段。

2. 规则库准备
   main() 调用 rbac/store.py 的 connect(db_path)：
   - sqlite3.connect(db_path) 打开规则文件；父目录存在而文件不存在时，
     SQLite 会创建新文件；
   - 随即执行模块常量 _SCHEMA（CREATE TABLE IF NOT EXISTS
     role_permissions，列为 role、permission，复合主键
     (role, permission)）并提交，确保表结构就绪；
   - 任何 sqlite3 层面的失败统一包装为 StorageError 抛出。
   main() 捕获 StorageError 后，经 _fail("storage_error") 向标准错误
   写入 {"error":"storage_error"} 加一个换行，return 1。
   核对位置：rbac/store.py connect()、_SCHEMA、StorageError；
   rbac/__main__.py main() 中 `except store.StorageError` 段、_fail()。

3. 只读导出全部授权规则
   main() 调用 rbac/store.py 的 list_all_rules(conn)：
   - 执行 SELECT role, permission FROM role_permissions（不带 WHERE、
     不带 ORDER BY 的整表只读查询）；
   - 在 Python 侧先经集合去重，再用 sorted() 排序：先按完整角色名的
     Unicode 码点升序，角色相同时按完整权限名的 Unicode 码点升序
     （元组比较的自然顺序）；
   - 返回 (role, permission) 元组列表；空表返回空列表；
   - 查询本身的 sqlite3 失败同样包装为 StorageError，由 main() 内层
     except 输出 storage_error、return 1。
   核对位置：rbac/store.py list_all_rules()；rbac/__main__.py main()
   中 export-rules 分支与内层 `except store.StorageError` 段。

4. JSON 输出
   main() 把元组列表组装为
   {"rules": [{"role": ..., "permission": ...}, ...]}，经 _emit() 以
   紧凑分隔符（ separators=(",", ":") ）、ensure_ascii=False 写入
   标准输出，并追加一个换行，return 0。每条规则对象只有 role 和
   permission 两个字段，顶层对象只有 rules 一个字段。
   核对位置：rbac/__main__.py main() 中 result 组装段、_emit()、
   _SEPARATORS。


二、导出内容的语义边界（核对"导出 vs 直接角色授权"时必读）
----------------------------------------------------------
1. 导出读取的是"角色 -> 权限"的授权组合本身，即 role_permissions 表的
   全部现存行。它与本地保存的直接角色授权一一对应：导出的每个
   {"role","permission"} 项就是一条已保存的授权规则，不多也不少。

2. 导出包含没有绑定任何固定成员的角色。例如角色 ghost 未出现在
   policy.FIXED_MEMBER_ROLES 中，只要 (ghost, 某权限) 已保存，就会原样
   出现在导出结果中。
   核对位置：tests/test_export_rules.py
   test_export_includes_roles_without_members。

3. 导出不代表任何成员的有效权限清单。成员的有效权限需要经
   policy.FIXED_MEMBER_ROLES 的固定成员-角色对应换算（那是
   list-member-permissions 命令的职责）；export-rules 不做这种换算，
   也不按成员过滤。

4. 导出不包含固定成员与角色的对应关系。该对应关系只存在于
   rbac/policy.py 的 FIXED_MEMBER_ROLES 常量（当前仅
   alice -> ("reader",)），不入库（rbac/store.py 模块 docstring 明确
   说明），因此也不会出现在导出 JSON 的任何字段中。

5. 名称按保存值原样返回：保留保存时的大小写与名称内部空白，导出环节
   不做裁剪、不做大小写折叠；星号 *、百分号 %、下划线 _ 都是普通字符，
   不作通配符解释。
   核对位置：rbac/store.py list_all_rules() docstring；
   tests/test_export_rules.py test_export_sorts_by_codepoint_and_
   preserves_names（含 "documents:*"、"documents:%"、"documents:_"
   与大小写混合角色名的样例）。

6. 同一（角色, 权限）组合在导出中只出现一次：表结构以 (role,
   permission) 为复合主键，grant 本身幂等，list_all_rules() 再做一次
   集合去重，双重保证不重复。
   核对位置：tests/test_export_rules.py
   test_export_after_duplicate_grant_still_unique_and_stable。

7. 导出是只读操作：list_all_rules() 只执行 SELECT，不写入、不删除。
   规则不变时重复导出结果完全一致；既有授权记录与其他表的数据在导出
   前后保持不变。
   核对位置：tests/test_export_rules.py test_export_is_read_only
   （含对额外 notes 表数据不变的核对）。


三、固定验收样例（命令、确定预期与实际执行记录）
------------------------------------------------
前提：父目录已存在、rules.db 尚不存在。以下命令在项目根目录执行
（当前环境用 python3 代替 python，下同）。

预置授权（三条命令各自预期退出码 0、标准错误为空、标准输出为对应的
{"role":...,"permission":...} 单行 JSON）：

    python -m rbac --db rules.db grant reader documents:read
    python -m rbac --db rules.db grant reader documents:write
    python -m rbac --db rules.db grant editor documents:read

执行导出：

    python -m rbac --db rules.db export-rules

确定预期：
- 退出码 0；
- 标准错误为空；
- 标准输出恰为下面一个紧凑 JSON 对象加结尾一个换行（除此之外无其他
  输出）：

    {"rules":[{"role":"editor","permission":"documents:read"},{"role":"reader","permission":"documents:read"},{"role":"reader","permission":"documents:write"}]}

- rules 数组依次包含：editor 的 documents:read、reader 的
  documents:read、reader 的 documents:write。顺序即第二节所述排序
  规则：角色名按 Unicode 码点升序（"editor" < "reader"），角色相同
  时权限名按码点升序（"documents:read" < "documents:write"）。
- 每项只有 role 和 permission 两个字段；顶层只有 rules 一个字段。

实际执行记录（本文写作时在临时目录执行，三条 grant 均退出码 0）：
- export-rules 退出码 0，标准错误为 0 字节；
- 标准输出与上面"确定预期"的 JSON 逐字节一致（含结尾换行）；
- 紧接着对同一规则库再次执行 export-rules，输出与首次完全一致。

对应测试：tests/test_export_rules.py
test_export_matches_acceptance_sample（同一样例与字段集合核对）、
test_export_after_duplicate_grant_still_unique_and_stable（重复导出
一致性）。


四、排序与名称细节的补充样例
----------------------------
tests/test_export_rules.py test_export_sorts_by_codepoint_and_
preserves_names 预置了 (b, 中)、(A, b)、(A, a)、(reader, documents:*)、
(reader, documents:%)、(reader, documents:_)、(Reader, documents:read)
七条授权，导出顺序为：

    A/a, A/b, Reader/documents:read, b/中,
    reader/documents:%, reader/documents:*, reader/documents:_

可见：大写字母码点小于小写（"A" < "Reader" < "b" < "reader"）；
"%"（U+0025）< "*"（U+002A）< "_"（U+005F），三者按普通字符参与码点
排序；大小写不同的 "Reader" 与 "reader" 是两个不同角色，各自独立成行。
该测试已在回归套件中实际通过（见"核对基准"的 104 tests OK）。


五、成功的空结果与两种存储副作用的区分
--------------------------------------
两种情形都返回成功空结果 {"rules":[]}（退出码 0、标准错误为空、标准
输出为 {"rules":[]} 加换行），但存储副作用不同，核对时应当区分：

1. 已有空规则库（文件与表已存在，表内无记录）
   复现方式：先 grant 再 revoke 同一组合造出空库，然后导出。
       python -m rbac --db empty.db grant reader documents:read
       python -m rbac --db empty.db revoke reader documents:read
       python -m rbac --db empty.db export-rules
   预期与实际执行记录一致：退出码 0，标准错误为空，标准输出恰为
   {"rules":[]} 加换行。副作用：无——不新建文件，不改动表结构与数据。
   对应测试：test_export_on_empty_database_returns_empty_rules。

2. 父目录存在但数据库文件缺失
       python -m rbac --db new.db export-rules   # new.db 事先不存在
   预期与实际执行记录一致：退出码 0，标准错误为空，标准输出恰为
   {"rules":[]} 加换行。副作用：connect() 会创建 new.db 这一可用的
   SQLite 规则库文件，并建立 role_permissions 表（实际观察到导出后
   new.db 已存在）。即"导出空结果"不代表"没有触碰存储"。
   对应测试：test_export_on_missing_db_initializes_and_returns_empty。

简言之：情形 1 是纯只读的空结果；情形 2 的空结果伴随"建库"副作用。
两者的 JSON 输出完全相同，只能通过对文件系统的观察区分。


六、存储失败与成功空结果的区别（三种失败样例）
----------------------------------------------
以下三种情形均不是成功空结果，而是存储失败：
- 退出码 1；
- 标准输出为空（0 字节，不输出 {"rules":...} 成功对象，也不输出任何
  异常堆栈）；
- 标准错误恰为一行 {"error":"storage_error"} 加一个换行。

1. 父目录不存在的路径
       python -m rbac --db no_such_dir/rules.db export-rules
   sqlite3 无法创建文件，connect() 抛 StorageError。
   实际执行记录：退出码 1，stdout 0 字节，stderr 恰为
   {"error":"storage_error"} 加换行；no_such_dir/rules.db 未被创建。
   对应测试：test_export_missing_parent_directory_is_storage_error。

2. 内容不是 SQLite 的既有文件（样例：连续 128 个 ASCII 字符 x）
   复现方式：printf 'x%.0s' $(seq 1 128) > bad.db，然后
       python -m rbac --db bad.db export-rules
   connect() 中的建表语句在不合法文件上失败，抛 StorageError。
   实际执行记录：退出码 1，stdout 0 字节，stderr 恰为
   {"error":"storage_error"} 加换行；bad.db 仍为原来的 128 字节、
   内容未被修复或覆盖。
   对应测试：test_export_non_sqlite_file_is_storage_error_and_untouched
   （测试用另一段非 SQLite 文本，属同一失败类别）。

3. role_permissions 表缺少 permission 列的既有 SQLite 文件
   复现方式：用 sqlite3 建库，只建
   CREATE TABLE role_permissions (role TEXT NOT NULL) 并插入一行
   ('reader')，然后
       python -m rbac --db partial.db export-rules
   connect() 的 CREATE TABLE IF NOT EXISTS 因表已存在而不改动结构；
   list_all_rules() 的 SELECT role, permission 因缺列失败，抛
   StorageError。
   实际执行记录：退出码 1，stdout 0 字节，stderr 恰为
   {"error":"storage_error"} 加换行；导出后表结构仍为单列
   (role TEXT NOT NULL)，('reader') 一行数据原样保留——导出不会自动
   补列、不修复结构、不改动既有数据。
   对应测试：test_export_table_missing_permission_column_is_
   storage_error。

与成功空结果的对比要点：{"rules":[]} 只出现在退出码 0、标准错误为空
的成功路径；只要存储层无法打开或读取规则库，输出就统一是标准错误上
的 {"error":"storage_error"}，标准输出不会有任何内容。核对导出内容
与本地授权是否一致时，应先确认退出码与标准错误，再比对 JSON。
