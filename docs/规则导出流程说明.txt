一、公开入口与从命令到 JSON 输出的完整路径
------------------------------------------
唯一公开入口是命令行：

    python -m rbac --db FILE export-rules [--role ROLE]

参数注册位置：rbac/__main__.py 的 _build_parser() 中
subparsers.add_parser("export-rules", ...)，该子命令不接收任何位置参数；
其上注册了可选参数 --role（argparse 中 default=None）。

一次调用从输入到输出严格按以下顺序执行（编排位置：rbac/__main__.py
的 main()）：

1. 参数解析与名称校验（--role 缺省跳过，显式传入时先于任何存储操作）
   argparse 解析 --db 路径与子命令。main() 对 export-rules 取
   raw_names：args.role 为 None（未传 --role）时 raw_names = ()（空
   元组，源码注释"--role 缺省（None）时全量导出，无需名称校验"），
   因此不带 --role 时不经过 policy.normalize_name()，也不可能触发
   invalid_name（退出码 2）分支，行为与新增筛选前完全一致。
   显式传入 --role（含空字符串 --role ''）时 raw_names = (args.role,)，
   名称先经 policy.normalize_name() 规整：去除首尾空白（str.strip，
   保留名称内部空白），去空白后为空则规整结果为 None。任一名称规整为
   None 时，main() 经 _fail("invalid_name") 向标准错误写入
   {"error":"invalid_name"} 加一个换行，return 2；该校验发生在
   store.connect() 之前，因此不会打开或创建数据库文件——即使 --db
   指向的父目录同时不存在，结果仍是退出码 2 而不是 storage_error。
   规整成功后得到目标角色名 target_name（去首尾空白后的保存值形态）。
   核对位置：rbac/__main__.py main() 中 export-rules 的 raw_names 段、
   normalized/invalid_name 段；rbac/policy.py normalize_name()。

2. 规则库准备
   main() 调用 rbac/store.py 的 connect(db_path)：
   - sqlite3.connect(db_path) 打开规则文件；父目录存在而文件不存在时，
     SQLite 会创建新文件；
   - 随即执行模块常量 _SCHEMA（CREATE TABLE IF NOT EXISTS
     role_permissions，列为 role、permission，复合主键
     (role, permission)）并提交，确保表结构就绪；
   - 任何 sqlite3 层面的失败统一包装为 StorageError 抛出。
   main() 捕获 StorageError 后，经 _fail("storage_error") 向标准错误
   写入 {"error":"storage_error"} 加一个换行，return 1。
   注意：名称校验（步骤 1）先于本步骤；只有名称有效（或未传 --role）
   时才会走到这里。
   核对位置：rbac/store.py connect()、_SCHEMA、StorageError；
   rbac/__main__.py main() 中 `except store.StorageError` 段、_fail()。

3. 只读导出授权规则（按是否传入 --role 走两个查询之一）
   main() 依据 target_name 是否为 None 选择查询：
   - 未传 --role：调用 rbac/store.py 的 list_all_rules(conn)，执行
     SELECT role, permission FROM role_permissions（不带 WHERE、不带
     ORDER BY 的整表只读查询）；
   - 传入有效 --role：调用 rbac/store.py 的 list_rules_for_role(conn,
     target_name)，执行
     SELECT role, permission FROM role_permissions WHERE role = ?，
     以规整后的完整角色名为绑定参数做大小写敏感精确匹配；"*"、"%"、
     "_" 都是普通参数字符，没有任何 LIKE/通配语义。
   两个查询都在 Python 侧先经集合去重，再用 sorted() 排序：先按完整
   角色名的 Unicode 码点升序，角色相同时按完整权限名的 Unicode 码点
   升序（元组比较的自然顺序）。按角色筛选时所有行的角色相同，实际
   效果即"权限按完整名称的 Unicode 码点升序"。两者均返回
   (role, permission) 元组列表，名称按保存值原样返回；表中无匹配行
   （角色从未出现、授权已全部撤销、空库）时返回空列表。
   查询本身的 sqlite3 失败（如表缺少必要列）同样包装为 StorageError，
   由 main() 内层 except 输出 storage_error、return 1。
   核对位置：rbac/store.py list_all_rules()、list_rules_for_role()；
   rbac/__main__.py main() 中 export-rules 分支与内层
   `except store.StorageError` 段。

4. JSON 输出
   main() 把元组列表组装为
   {"rules": [{"role": ..., "permission": ...}, ...]}，经 _emit() 以
   紧凑分隔符（ separators=(",", ":") ）、ensure_ascii=False 写入
   标准输出，并追加一个换行，return 0。无论是否按角色筛选，每条规则
   对象都只有 role 和 permission 两个字段，顶层对象只有 rules 一个
   字段；筛选只改变 rules 数组的成员，不改变其元素形态与输出编码。
   核对位置：rbac/__main__.py main() 中 result 组装段、_emit()、
   _SEPARATORS。


二、导出内容的语义边界（核对"导出 vs 直接角色授权"时必读）
----------------------------------------------------------
1. 导出读取的是"角色 -> 权限"的授权组合本身，即 role_permissions 表的
   现存行。它与本地保存的直接角色授权一一对应：导出的每个
   {"role","permission"} 项就是一条已保存的授权规则，不多也不少。
   不带 --role 时读取全部现存行；带 --role ROLE 时只读取
   role = 规整后 ROLE 的现存行，是当前授权规则的筛选结果，不做成员
   换算、不做通配展开，也不补全角色。

2. 导出包含没有绑定任何固定成员的角色。例如角色 ghost 未出现在
   policy.FIXED_MEMBER_ROLES 中，只要 (ghost, 某权限) 已保存，就会原样
   出现在全量导出结果中；带 --role ghost 时也同样正常导出该角色的授权
   片段——筛选条件只看 role_permissions 中是否存在该角色的授权，与是否
   配置了固定成员无关。
   核对位置：tests/test_export_rules.py
   test_export_includes_roles_without_members、
   test_export_role_includes_roles_without_members。

3. 导出不代表任何成员的有效权限清单。成员的有效权限需要经
   policy.FIXED_MEMBER_ROLES 的固定成员-角色对应换算（那是
   list-member-permissions 命令的职责）；export-rules 即使带 --role
   也不做这种换算，也不按成员过滤。

4. 导出不包含固定成员与角色的对应关系。该对应关系只存在于
   rbac/policy.py 的 FIXED_MEMBER_ROLES 常量（当前仅
   alice -> ("reader",)），不入库（rbac/store.py 模块 docstring 明确
   说明），因此也不会出现在导出 JSON 的任何字段中。--role reader 的
   结果中不包含任何成员信息。

5. 名称按保存值原样返回：保留保存时的大小写与名称内部空白，导出环节
   不做裁剪、不做大小写折叠；星号 *、百分号 %、下划线 _ 都是普通字符，
   不作通配符解释。带 --role 时匹配规则相同：先对入参去首尾空白
   （normalize_name），再以完整名称做大小写敏感的等值比较
   （WHERE role = ?，无 LIKE）；"Reader" 不匹配 "reader"，"reader%"
   只匹配保存名恰为 "reader%" 的角色，内部空白不同的名称互不匹配；
   输出中的角色名仍是保存值（不含被裁掉的首尾空白）。
   核对位置：rbac/store.py list_all_rules()、list_rules_for_role()
   docstring；tests/test_export_rules.py
   test_export_sorts_by_codepoint_and_preserves_names、
   test_export_role_trims_whitespace_matches_exactly_and_case_sensitively。

6. 同一（角色, 权限）组合在导出中只出现一次：表结构以 (role,
   permission) 为复合主键，grant 本身幂等，list_all_rules() 与
   list_rules_for_role() 都再做一次集合去重，双重保证不重复。
   核对位置：tests/test_export_rules.py
   test_export_after_duplicate_grant_still_unique_and_stable。

7. 导出是只读操作：list_all_rules() 与 list_rules_for_role() 都只执行
   SELECT，不写入、不删除。规则不变时重复导出结果完全一致（全量与按
   角色均然）；既有授权记录与其他表的数据在导出前后保持不变。
   核对位置：tests/test_export_rules.py test_export_is_read_only
   （含对额外 notes 表数据不变的核对）、
   test_export_role_is_read_only_stable_and_same_shape_without_filter。

8. 不带 --role 的全量导出与新增筛选前逐字节一致：同一个库上，全量
   导出的内容、排序、JSON 形态、退出码都不因本次改动而变化（见第三节
   全量样例与上述稳定性测试）。


三、固定验收样例（命令、确定预期与实际执行记录）
------------------------------------------------
前提：父目录已存在、rules.db 尚不存在。以下命令在项目根目录执行
（当前环境用 python3 代替 python，下同）。

预置授权（三条命令各自预期退出码 0、标准错误为空、标准输出为对应的
{"role":...,"permission":...} 单行 JSON）：

    python -m rbac --db rules.db grant reader documents:read
    python -m rbac --db rules.db grant reader documents:write
    python -m rbac --db rules.db grant editor documents:read

执行导出（全量）：

    python -m rbac --db rules.db export-rules

确定预期：
- 退出码 0；
- 标准错误为空；
- 标准输出恰为下面一个紧凑 JSON 对象加结尾一个换行（除此之外无其他
  输出）：

    {"rules":[{"role":"editor","permission":"documents:read"},{"role":"reader","permission":"documents:read"},{"role":"reader","permission":"documents:write"}]}

- rules 数组依次包含：editor 的 documents:read、reader 的
  documents:read、reader 的 documents:write。顺序即第二节所述排序
  规则：角色名按 Unicode 码点升序（"editor" < "reader"），角色相同
  时权限名按码点升序（"documents:read" < "documents:write"）。
- 每项只有 role 和 permission 两个字段；顶层只有 rules 一个字段。

按角色筛选导出：

    python -m rbac --db rules.db export-rules --role reader

确定预期（筛选）：
- 退出码 0，标准错误为空，标准输出恰为（加结尾换行）：

    {"rules":[{"role":"reader","permission":"documents:read"},{"role":"reader","permission":"documents:write"}]}

- 只含 reader 的两条，依次为 documents:read、documents:write；
  editor 的 documents:read 不出现在结果中，但仍保存在库内
  （export-rules --role editor 仍可取出它）。

实际执行记录（本次更新时在临时目录执行，三条 grant 均退出码 0）：
- export-rules 与 export-rules --role reader 均退出码 0，标准错误为
  0 字节，标准输出分别与上面两个"确定预期"的 JSON 逐字节一致
  （含结尾换行）；
- 紧接着对同一规则库再次执行同样的导出，输出与首次完全一致。

对应测试：tests/test_export_rules.py
test_export_matches_acceptance_sample（全量样例与字段集合核对）、
test_export_role_matches_acceptance_sample（--role reader/editor
筛选样例）、
test_export_after_duplicate_grant_still_unique_and_stable（重复导出
一致性）、
test_export_role_is_read_only_stable_and_same_shape_without_filter
（带筛选的稳定性与全量形态不变）。

五、成功的空结果与两种存储副作用的区分
--------------------------------------
以下情形都返回成功空结果 {"rules":[]}（退出码 0、标准错误为空、标准
输出为 {"rules":[]} 加换行），但存储副作用不同，核对时应当区分。全量
导出与带有效 --role 的筛选导出在每种情形下的 JSON 与退出码都相同。

1. 已有空规则库（文件与表已存在，表内无记录）
   复现方式：先 grant 再 revoke 同一组合造出空库，然后导出。
       python -m rbac --db empty.db grant reader documents:read
       python -m rbac --db empty.db revoke reader documents:read
       python -m rbac --db empty.db export-rules
       python -m rbac --db empty.db export-rules --role reader
   预期与实际执行记录一致：两条导出均退出码 0，标准错误为空，标准
   输出恰为 {"rules":[]} 加换行。带 --role 时，角色从未出现或该角色
   授权已全部撤销（如 --role ghost、--role reader）同样是该成功空
   结果，不是错误。副作用：无——不新建文件，不改动表结构与数据。
   对应测试：test_export_on_empty_database_returns_empty_rules、
   test_export_role_unknown_revoked_and_empty_database。

2. 父目录存在但数据库文件缺失
       python -m rbac --db new.db export-rules
       python -m rbac --db new.db export-rules --role reader
   预期与实际执行记录一致：退出码 0，标准错误为空，标准输出恰为
   {"rules":[]} 加换行。副作用：connect() 会创建 new.db 这一可用的
   SQLite 规则库文件，并建立 role_permissions 表（实际观察到导出后
   new.db 已存在）。即"导出空结果"不代表"没有触碰存储"。
   对应测试：test_export_on_missing_db_initializes_and_returns_empty、
   test_export_role_unknown_revoked_and_empty_database。

简言之：情形 1 是纯只读的空结果；情形 2 的空结果伴随"建库"副作用。
两者的 JSON 输出完全相同，只能通过对文件系统的观察区分。


六、名称校验失败与存储失败（均非正常成功，且名称校验优先）
----------------------------------------------------------
本节区分两类失败；二者都不输出成功 JSON 对象。

（A）名称无效——仅可能发生在显式传入 --role 时：
- 退出码 2；
- 标准输出为空（0 字节）；
- 标准错误恰为一行 {"error":"invalid_name"} 加一个换行。
触发方式：--role ''（空字符串）或 --role '   '（纯空白，含制表符与
换行的组合）。名称规整（去首尾空白）发生在 store.connect() 之前，
因此：
- 不会打开或创建数据库文件，不改动任何已有授权；
- 即使 --db 路径同时无效（如父目录不存在），结果仍是退出码 2 的
  invalid_name，而不是 storage_error，无效路径上的文件与父目录都不会
  被创建。
实际执行记录（本次更新时在临时目录执行）：对已有三条授权的库执行
export-rules --role '' 与 --role '   '，均退出码 2、stdout 0 字节、
stderr 恰为 {"error":"invalid_name"} 加换行，库内三条授权原样保留；
对 --db no_such_dir/x.db 配合空 --role 的调用，结果相同，且
no_such_dir 目录未被创建。
对应测试：
test_export_role_blank_name_is_invalid_name_without_storage_access。
不带 --role 的全量导出不接收名称，不存在该失败路径。

（B）存储失败——名称有效（或未传 --role），但存储层无法打开或读取：
- 退出码 1；
- 标准输出为空（0 字节，不输出 {"rules":...} 成功对象，也不输出任何
  异常堆栈）；
- 标准错误恰为一行 {"error":"storage_error"} 加一个换行。

1. 父目录不存在的路径
       python -m rbac --db no_such_dir/rules.db export-rules
       python -m rbac --db no_such_dir/rules.db export-rules --role reader
   sqlite3 无法创建文件，connect() 抛 StorageError。
   实际执行记录：退出码 1，stdout 0 字节，stderr 恰为
   {"error":"storage_error"} 加换行；no_such_dir/rules.db 未被创建。
   对应测试：test_export_missing_parent_directory_is_storage_error、
   test_export_role_missing_parent_directory_is_storage_error。

2. 内容不是 SQLite 的既有文件（样例：连续 128 个 ASCII 字符 x）
   复现方式：printf 'x%.0s' $(seq 1 128) > bad.db，然后
       python -m rbac --db bad.db export-rules
       python -m rbac --db bad.db export-rules --role reader
   connect() 中的建表语句在不合法文件上失败，抛 StorageError。
   实际执行记录：退出码 1，stdout 0 字节，stderr 恰为
   {"error":"storage_error"} 加换行；bad.db 仍为原来的 128 字节、
   内容未被修复或覆盖。
   对应测试：test_export_non_sqlite_file_is_storage_error_and_untouched
   （全量）、
   test_export_role_non_sqlite_file_is_storage_error_and_untouched
   （--role，测试用另一段非 SQLite 文本，属同一失败类别）。

3. role_permissions 表缺少 permission 列的既有 SQLite 文件
   复现方式：用 sqlite3 建库，只建
   CREATE TABLE role_permissions (role TEXT NOT NULL) 并插入一行
   ('reader')，然后
       python -m rbac --db partial.db export-rules
       python -m rbac --db partial.db export-rules --role reader
   connect() 的 CREATE TABLE IF NOT EXISTS 因表已存在而不改动结构；
   全量路径 list_all_rules() 的 SELECT role, permission、筛选路径
   list_rules_for_role() 的同列 SELECT ... WHERE role = ? 均因缺列
   失败，抛 StorageError。
   实际执行记录：退出码 1，stdout 0 字节，stderr 恰为
   {"error":"storage_error"} 加换行；导出后表结构仍为单列
   (role TEXT NOT NULL)，('reader') 一行数据原样保留——导出不会自动
   补列、不修复结构、不改动既有数据。
   对应测试：test_export_table_missing_permission_column_is_
   storage_error、
   test_export_role_table_missing_permission_column_is_storage_error。

与成功空结果的对比要点：{"rules":[]} 只出现在退出码 0、标准错误为空
的成功路径；名称无效时是退出码 2 的 {"error":"invalid_name"}（先于
一切存储操作）；存储层无法打开或读取时是退出码 1 的
{"error":"storage_error"}，标准输出都不会有任何内容。核对导出内容与
本地授权是否一致时，应先确认退出码与标准错误，再比对 JSON。
