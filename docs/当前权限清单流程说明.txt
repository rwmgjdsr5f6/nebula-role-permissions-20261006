一、公开入口与从命令到结果的完整路径
------------------------------------
唯一公开入口是命令行：

    python -m rbac --db FILE list-all-permissions

参数注册位置：rbac/__main__.py 的 _build_parser() 中
subparsers.add_parser("list-all-permissions", ...)，该子命令不接收任何
位置参数（没有角色、成员或权限名称参数）。

一次调用从输入到输出严格按以下顺序执行（编排位置：rbac/__main__.py
的 main()）：

1. 参数解析与名称校验的跳过
   argparse 解析 --db 路径与子命令。main() 对 list-all-permissions 取
   raw_names = ()（空元组，与 export-rules、list-roles 同一段，源码注释
   "不接收成员、角色或权限参数，无需名称校验"），因此本命令不经过
   policy.normalize_name() 的名称规整，也不可能触发 invalid_name
   （退出码 2）分支。
   核对位置：rbac/__main__.py main() 中 `if args.command in
   ("export-rules", "list-roles", "list-all-permissions"): raw_names = ()`
   段。

2. 规则库准备
   main() 调用 rbac/store.py 的 connect(db_path)：
   - sqlite3.connect(db_path) 打开规则文件；父目录存在而文件不存在时，
     SQLite 会创建新文件；
   - 随即执行模块常量 _SCHEMA（CREATE TABLE IF NOT EXISTS
     role_permissions，列为 role、permission，复合主键
     (role, permission)）并提交，确保授权表结构就绪；
   - 任何 sqlite3 层面的失败统一包装为 StorageError 抛出。
   main() 捕获 StorageError 后，经 _fail("storage_error") 向标准错误
   写入 {"error":"storage_error"} 加一个换行，return 1。
   核对位置：rbac/store.py connect()、_SCHEMA、StorageError；
   rbac/__main__.py main() 中 `except store.StorageError` 段、_fail()。

3. 只读查询全部权限名、去重排序
   main() 走 `elif args.command == "list-all-permissions":` 分支，调用
   rbac/store.py 的 list_all_permissions(conn)：
   - 执行 SELECT permission FROM role_permissions（不带 WHERE、不带
     ORDER BY 的整表只读查询，只取 permission 一列）；
   - 在 Python 侧先经集合去重（同名权限只保留一个），再用 sorted()
     按完整权限名的 Unicode 码点顺序升序排列；
   - 返回权限名列表；空表返回空列表；
   - 查询本身的 sqlite3 失败同样包装为 StorageError，由 main() 内层
     except 输出 storage_error、return 1。
   核对位置：rbac/store.py list_all_permissions()；rbac/__main__.py
   main() 中 list-all-permissions 分支与内层 `except store.StorageError`
   段。

4. JSON 输出
   main() 把权限名列表组装为 {"permissions": [...]}，经 _emit() 以紧凑
   分隔符（separators=(",", ":")）、ensure_ascii=False 写入标准输出，
   并追加一个换行，return 0。顶层对象只有 permissions 一个字段。
   核对位置：rbac/__main__.py main() 中 result 组装段、_emit()、
   _SEPARATORS。

5. 连接关闭
   无论查询成功还是抛出 StorageError，main() 的 finally 块都会执行
   conn.close() 关闭数据库连接，再输出结果或错误。
   核对位置：rbac/__main__.py main() 中 `finally: conn.close()` 段。


二、清单内容的语义边界（核对"清单 vs 有效权限"时必读）
------------------------------------------------------
1. 清单汇总的是库中当前所有角色直接获授的权限名，即 role_permissions
   表 permission 列的现存值全集。只要任一角色仍持有某权限的直接授权，
   该权限名就在清单中。

2. 未绑定成员的角色所持权限同样计入。例如角色 ghost 未出现在
   policy.FIXED_MEMBER_ROLES 中，只要 (ghost, 某权限) 已保存，该权限名
   就会出现在清单中。
   核对位置：tests/test_list_all_permissions.py
   test_list_includes_permissions_of_roles_without_members。

3. 同名权限只出现一次：表结构以 (role, permission) 为复合主键，
   list_all_permissions() 再做一次集合去重，多个角色持有同名权限时
   清单中仍只出现一次。
   核对位置：tests/test_list_all_permissions.py
   test_list_deduplicates_sorts_by_codepoint_and_preserves_names。

4. 排序按完整权限名的 Unicode 码点升序：大写字母码点小于小写字母，
   中文等字符按其码点排在 ASCII 之后。名称按保存值原样返回，保留保存
   时的大小写与名称内部空白，不做裁剪、不做大小写折叠；星号 *、百分号
   %、下划线 _ 都是普通字符，不作通配符解释（"%"（U+0025）< "*"（U+002A）
   < "_"（U+005F），按普通字符参与码点排序）。
   核对位置：rbac/store.py list_all_permissions() docstring；
   tests/test_list_all_permissions.py
   test_list_deduplicates_sorts_by_codepoint_and_preserves_names
   （含 "Documents:Read"、"with  space"、"documents:*"、"documents:%"、
   "documents:_"、"中" 的样例，预期顺序为 Documents:Read、a、b、
   documents:%、documents:*、documents:_、with  space、中）。

5. 固定成员关系不参与本查询。policy.FIXED_MEMBER_ROLES（当前仅
   alice -> ("reader",)）只在 check、list-member-permissions 等命令中
   使用；list-all-permissions 的代码路径不调用 policy.py 的任何函数。
   因此清单不是 alice（或任何成员）的有效权限清单——成员的有效权限需要
   经固定成员-角色对应换算，那是 list-member-permissions 命令的职责。
   核对位置：rbac/__main__.py main() 中 list-all-permissions 分支
   （仅调用 store.list_all_permissions）。

6. 清单也不代表一份独立保存的"权限目录"。数据库中只保存"角色 -> 权限"
   这一类规则（rbac/store.py 模块 docstring 明确说明），不存在单独的
   权限表；清单是授权记录的派生视图，权限名只能随授权的出现而出现、
   随最后一条同名授权的撤销而消失。


三、固定验收样例（命令、确定预期与实际执行记录）
------------------------------------------------
前提：父目录已存在、rules.db 尚不存在。以下命令在项目根目录执行
（当前环境用 python3 代替 python，下同）。

预置授权（三条命令各自预期退出码 0、标准错误为空、标准输出为对应的
{"role":...,"permission":...} 单行 JSON）：

    python -m rbac --db rules.db grant reader documents:read
    python -m rbac --db rules.db grant editor documents:read
    python -m rbac --db rules.db grant editor documents:write

即 reader 与 editor 都持有 documents:read，editor 另持有
documents:write。

执行清单查询：

    python -m rbac --db rules.db list-all-permissions

确定预期：
- 退出码 0；
- 标准错误为空；
- 标准输出恰为下面一个紧凑 JSON 对象加结尾一个换行（除此之外无其他
  输出）：

    {"permissions":["documents:read","documents:write"]}

- permissions 数组依次包含 documents:read、documents:write，顺序即
  第二节所述排序规则（"documents:read" < "documents:write" 的码点
  升序）；同名权限 documents:read 虽被两个角色持有，只出现一次；
  顶层只有 permissions 一个字段。

实际执行记录（本文写作时在临时目录执行，三条 grant 均退出码 0）：
- list-all-permissions 退出码 0，标准错误为 0 字节；
- 标准输出共 53 字节，与上面"确定预期"的 JSON 逐字节一致（52 个
  ASCII 字符加结尾一个换行）。

对应测试：tests/test_list_all_permissions.py
test_list_matches_acceptance_sample。注意该测试的预置样例与本文第三节
略有差别：测试的第三条授权是 reader/documents:write（而非
editor/documents:write），两者得到的清单完全相同，均为
["documents:read","documents:write"]——清单只反映权限名的现存集合，
不反映持有者是谁。

为何只撤销 reader 的读取授权清单不变：
    python -m rbac --db rules.db revoke reader documents:read
之后 editor 仍持有 documents:read 的直接授权，role_permissions 表中
permission 列仍同时存在 documents:read 与 documents:write，故清单不变。
实际执行记录：revoke 退出码 0（输出
{"role":"reader","permission":"documents:read","revoked":true}），随后
list-all-permissions 退出码 0，标准输出仍为
{"permissions":["documents:read","documents:write"]} 加换行。
对应测试：test_revoke_keeps_permission_while_other_role_holds_it。

为何最后一条同名授权撤销后该权限消失：
    python -m rbac --db rules.db revoke editor documents:read
之后库中不再有任何角色持有 documents:read，清单是授权记录的派生视图，
该权限名随之消失。实际执行记录：revoke 退出码 0，随后
list-all-permissions 退出码 0，标准输出为
{"permissions":["documents:write"]} 加换行。
对应测试：test_permission_disappears_after_last_grant_revoked。


四、查询的只读性
----------------
list_all_permissions() 只执行 SELECT，不写入、不删除。规则不变时重复
查询结果完全一致；既有授权记录与其他表的数据在查询前后保持不变。
对应测试：tests/test_list_all_permissions.py test_list_is_read_only
（查询前后比对授权记录，并核对额外建立的 notes 表数据不变）。
唯一的存储副作用发生在规则库准备环节（connect() 的建库建表），且仅在
数据库文件或表尚不存在时发生，见第五节情形 2。


五、成功的空结果与两种存储情形的区分
------------------------------------
两种情形都返回成功空结果 {"permissions":[]}（退出码 0、标准错误为空、
标准输出为 {"permissions":[]} 加换行），但存储情形不同，核对时应当
区分：

1. 已有空规则库（文件与授权表已存在，表内无记录）
   复现方式：先 grant 再 revoke 同一组合造出空库，然后查询。
       python -m rbac --db empty.db grant reader documents:read
       python -m rbac --db empty.db revoke reader documents:read
       python -m rbac --db empty.db list-all-permissions
   预期与实际执行记录一致：退出码 0，标准错误为空，标准输出恰为
   {"permissions":[]} 加换行。副作用：无——不新建文件，不改动表结构
   与数据。
   对应测试：test_list_on_empty_database_returns_empty_permissions。

2. 父目录存在且可写，但规则文件缺失
       python -m rbac --db new.db list-all-permissions   # new.db 事先不存在
   预期与实际执行记录一致：退出码 0，标准错误为空，标准输出恰为
   {"permissions":[]} 加换行。副作用：connect() 会创建 new.db 这一可用
   的 SQLite 规则库文件，并建立 role_permissions 授权表（实际观察到
   查询后 new.db 已存在，内含标准的 role_permissions 建表语句）。即
   "清单为空"不代表"没有触碰存储"。
   对应测试：test_list_on_missing_db_initializes_and_returns_empty。

简言之：情形 1 是纯只读的空结果；情形 2 的空结果伴随"建库建表"副作用。
两者的 JSON 输出完全相同，只能通过对文件系统的观察区分。


六、存储失败与成功空结果的区别（三种失败样例）
----------------------------------------------
以下三种情形均不是成功空结果，而是存储失败：
- 退出码 1；
- 标准输出为空（0 字节，不输出 {"permissions":...} 成功对象，也不输出
  任何异常堆栈）；
- 标准错误恰为一行 {"error":"storage_error"} 加一个换行；
- 不自动修复、不覆盖原文件。

1. 父目录不存在的路径
       python -m rbac --db no_such_dir/rules.db list-all-permissions
   sqlite3 无法创建文件，connect() 抛 StorageError。
   实际执行记录：退出码 1，stdout 0 字节，stderr 恰为
   {"error":"storage_error"} 加换行；no_such_dir/rules.db 未被创建。
   对应测试：test_list_missing_parent_directory_is_storage_error。

2. 内容不是 SQLite 的既有文件（样例：文本 "this is not a sqlite
   database"，29 字节）
   复现方式：把该文本写入 bad.db，然后
       python -m rbac --db bad.db list-all-permissions
   connect() 中的建表语句在不合法文件上失败，抛 StorageError。
   实际执行记录：退出码 1，stdout 0 字节，stderr 恰为
   {"error":"storage_error"} 加换行；bad.db 仍为原来的 29 字节、内容
   未被修复或覆盖。
   对应测试：test_list_non_sqlite_file_is_storage_error_and_untouched。

3. role_permissions 表缺少 permission 列的既有 SQLite 文件
   复现方式：用 sqlite3 建库，只建
   CREATE TABLE role_permissions (role TEXT NOT NULL) 并插入一行
   ('reader')，然后
       python -m rbac --db partial.db list-all-permissions
   connect() 的 CREATE TABLE IF NOT EXISTS 因表已存在而不改动结构；
   list_all_permissions() 的 SELECT permission 因缺列失败，抛
   StorageError。
   实际执行记录：退出码 1，stdout 0 字节，stderr 恰为
   {"error":"storage_error"} 加换行；查询后表结构仍为单列
   (role TEXT NOT NULL)，('reader') 一行数据原样保留——查询不会自动
   补列、不修复结构、不改动既有数据。
   对应测试：test_list_table_missing_permission_column_is_storage_error。

与成功空结果的对比要点：{"permissions":[]} 只出现在退出码 0、标准错误
为空的成功路径；只要存储层无法打开或读取规则库，输出就统一是标准错误
上的 {"error":"storage_error"}，标准输出不会有任何内容。核对清单内容
与本地授权是否一致时，应先确认退出码与标准错误，再比对 JSON。

另外，本命令没有名称位置参数（见第一节），不会触发 invalid_name
（退出码 2）分支；invalid_name 只可能出现在带名称参数的子命令上。
