一、公开入口与实际执行顺序
--------------------------
本文涉及的两个公开入口（在 rbac/__main__.py 的 _build_parser() 注册）：

    python -m rbac --db FILE grant ROLE PERMISSION
    python -m rbac --db FILE check MEMBER PERMISSION

其余子命令（revoke、list-*、export-rules）见 README“全部命令”，行为
保持不变，本文不涉及。

一次 grant/check 调用从输入到输出，严格按以下五步顺序执行
（编排位置：rbac/__main__.py 的 main()）：

1. 命令行解析
   argparse 解析 --db 路径与子命令参数：grant 取 role、permission；
   check 取 member、permission。
   核对位置：rbac/__main__.py _build_parser()、main() 开头。

2. 名称规整（先于一切存储操作）
   名称参数先经 policy.normalize_name() 处理：str.strip() 去除首尾
   空白，之后按完整字符串做大小写敏感匹配；去空白后为空（空字符串或
   纯空白）时返回 None。main() 发现任一名称为 None，立即调用 _fail()
   输出 invalid_name 并返回退出码 2——此分支发生在 store.connect()
   之前，因此不会打开或创建数据库文件。
   核对位置：rbac/policy.py normalize_name()；rbac/__main__.py
   main() 中 normalized 校验段（注释“不打开存储、不改动任何已有授权”）。

3. 数据库准备
   名称全部有效后，store.connect(db_path) 打开规则文件，并执行
   _SCHEMA 中的 CREATE TABLE IF NOT EXISTS role_permissions（复合主键
   (role, permission)）后提交；文件尚不存在而父目录可写时，这一步会
   创建文件并初始化空表。连接或初始化中的任何 sqlite3.Error 统一包装
   为 store.StorageError，由 main() 调用 _fail() 输出 storage_error、
   返回退出码 1。
   核对位置：rbac/store.py connect()、_SCHEMA、StorageError；
   rbac/__main__.py main() 中包裹 store.connect() 的 try/except。

4. 固定角色读取与直接授权匹配
   - 成员关系来自固定配置，不来自数据库：policy.roles_for(member)
     从 policy.FIXED_MEMBER_ROLES 读取成员的直接角色列表。当前固定
     配置只有 alice -> ("reader",)；未配置成员得到空列表。grant 只
     写“角色 -> 权限”规则，任何命令都无法改变这一对应关系。
   - check 的匹配在 store.permission_granted(conn, roles, permission)
     中完成：角色列表为空时直接返回 False，不查询规则表；非空时执行
     只读 SELECT，查这些角色中是否有任一直接拥有请求权限；查询中的
     sqlite3.Error 包装为 StorageError。
   - grant 的写入在 store.grant_permission() 中完成：先按规整后的
     （角色, 权限）组合精确查询，组合已存在则按幂等成功返回；不存在
     时普通 INSERT、提交并复查该行确实可读回。
   - 数据边界：SQLite 中只保存“角色 -> 权限”一类规则，成员-角色
     对应不入库（rbac/store.py 模块 docstring 与 policy.FIXED_MEMBER_ROLES
     注释均明确说明）。
   核对位置：rbac/policy.py FIXED_MEMBER_ROLES、roles_for()；
   rbac/store.py permission_granted()、grant_permission()。

5. 结果输出
   check 由 policy.decide() 依据角色与匹配结果生成决定，原因取
   policy.py 的三个固定常量：
   - 角色列表为空 -> allowed=false，reason="成员未配置"
     （REASON_MEMBER_NOT_CONFIGURED）；
   - 有角色且命中规则 -> allowed=true，reason="直接角色授权"
     （REASON_ALLOWED）；
   - 有角色但未命中 -> allowed=false，reason="权限未授予"
     （REASON_PERMISSION_NOT_GRANTED）。
   main() 用 _emit() 把结果写成紧凑 JSON（separators=(",",":")、
   ensure_ascii=False，中文原因原样输出）并追加一个换行；标准输出与
   标准错误在 main() 开头统一 reconfigure 为 UTF-8。成功返回退出码 0。
   核对位置：rbac/policy.py decide() 及 REASON_* 常量；
   rbac/__main__.py _emit()、_fail()。

顺序要点（第三节的两个边界都由此而来）：数据库准备（第 3 步）先于
固定角色读取（第 4 步）；而规则表查询只对非空角色发生。因此初始化
本身失败时，任何成员都拿不到业务结果；初始化可完成、仅缺业务列时，
空角色成员仍可不查询规则表而正常返回。


二、主流程样例（源码可核对的预期输出）
--------------------------------------
前提：当前工作目录（即规则文件的父目录）存在且可写，rules.db 尚不
存在。以下命令在该目录执行。

1) 授予 reader 权限 documents:read：

    python -m rbac --db rules.db grant reader documents:read

   预期：退出码 0；标准错误为空；标准输出恰为单行 UTF-8 JSON 加一个
   换行：

    {"role":"reader","permission":"documents:read"}

   副作用：创建 rules.db 与 role_permissions 表，写入一条
   (reader, documents:read) 记录。重复执行同一 grant 为幂等成功，
   表中不增加记录（见 grant_permission() 的写入前精确查询）。

2) 查询 alice 是否拥有 documents:read：

    python -m rbac --db rules.db check alice documents:read

   预期：退出码 0；标准错误为空；标准输出恰为：

    {"member":"alice","permission":"documents:read","roles":["reader"],"allowed":true,"reason":"直接角色授权"}

   即：alice 的角色为 ["reader"]，allowed 为 true，原因是“直接角色
   授权”。

3) 同库查询未授予的 documents:write：

    python -m rbac --db rules.db check alice documents:write

   预期：退出码 0；标准错误为空；标准输出恰为：

    {"member":"alice","permission":"documents:write","roles":["reader"],"allowed":false,"reason":"权限未授予"}

   alice 有角色 reader，但库中没有 (reader, documents:write) 规则，
   故 allowed 为 false，原因为“权限未授予”。

4) 同库查询未配置成员 bob：

    python -m rbac --db rules.db check bob documents:read

   预期：退出码 0；标准错误为空；标准输出恰为：

    {"member":"bob","permission":"documents:read","roles":[],"allowed":false,"reason":"成员未配置"}

   bob 不在 FIXED_MEMBER_ROLES 中，roles 为 []，allowed 为 false，
   原因为“成员未配置”。

以上四步的预期均为退出码 0、标准错误为空、标准输出为单行 UTF-8 JSON
加一个换行。后三步是对同一 rules.db 的只读查询，不改变任何授权记录。


三、拒绝与执行失败的区分
------------------------
allowed=false 的拒绝是正常业务结果（退出码 0），必须与退出码非 0 的
执行失败分开。

1. 正常拒绝（退出码 0，输出判定 JSON）
   - “权限未授予”：成员有直接角色，但库中没有对应角色 -> 权限规则，
     见第二节第 3 步；
   - “成员未配置”：成员不在固定配置中、角色为空，见第二节第 4 步。
   判定位置：rbac/policy.py decide()。

2. 名称规整与大小写
   名称先去首尾空白，再按完整字符串大小写敏感匹配。例如 "Alice" 不会
   命中固定成员 "alice"（按未配置成员处理，roles 为 []，原因“成员未
   配置”）；"documents:Read" 不会命中已授予的 "documents:read"（原因
   “权限未授予”）。
   核对位置：rbac/policy.py normalize_name()、FIXED_MEMBER_ROLES。

3. 名称无效（退出码 2，优先于一切存储操作）
   任一名称去首尾空白后为空（空字符串或纯空白）时：
   - 退出码 2；
   - 标准输出为空；
   - 标准错误恰为一行 {"error":"invalid_name"} 加一个换行；
   - 不打开、不创建数据库文件（rules.db 不存在时仍不存在），也不改动
     任何已有授权。
   即使同时满足下面的存储失败条件（如父目录也不存在、文件不是
   SQLite、表结构缺列），名称无效仍然优先，因为该校验在 main() 中
   先于 store.connect()。
   核对位置：rbac/__main__.py main() 中 normalized 校验段、_fail()。

4. 存储失败（退出码 1）
   名称有效，但规则文件无法打开、初始化或读写时：退出码 1；标准输出
   为空（不得夹带任何业务 JSON）；标准错误恰为一行
   {"error":"storage_error"} 加一个换行，不附加详情或堆栈。
   核对位置：rbac/store.py StorageError 及 connect()、
   permission_granted()、grant_permission() 中的包装；
   rbac/__main__.py main() 的两处 except store.StorageError。

   典型情形：
   a. 父目录不存在：sqlite3 无法创建文件，connect() 包装为
      StorageError。
   b. 文件存在但不是 SQLite 数据库：连接可能建立，但 connect() 内的
      建表初始化（CREATE TABLE IF NOT EXISTS）必然失败——失败发生在
      固定角色读取与业务查询之前，因此即使查询 bob（正常库上本应返回
      “成员未配置”）也只能得到退出码 1；文件原有字节不被清空或修补。
      对照：tests/test_non_sqlite_rulefile.py。
   c. 规则表缺少 permission 列但初始化可完成：CREATE TABLE IF NOT
      EXISTS 对已存在的表为空操作，connect() 正常返回。此后——
      - 查询 alice：其角色非空，permission_granted() 必须读取
        permission 列，sqlite3.Error 包装为 StorageError，退出码 1、
        stdout 为空、stderr 为 {"error":"storage_error"}；
      - 查询 bob：roles_for() 返回空列表，permission_granted()
        直接返回 False 而不触碰规则表，decide() 照常给出退出码 0 的
        {"member":"bob",...,"roles":[],"allowed":false,
        "reason":"成员未配置"}，缺列不影响该结果。
      即“缺权限列但初始化可完成时，bob 仍正常返回成员未配置；非
      SQLite 文件的初始化失败则先于该结果”。
      对照：tests/test_incompatible_schema.py。
   d. grant 写入被既有表约束阻止（如单列唯一约束、CHECK 约束）：
      普通 INSERT 的 sqlite3.Error 在 grant_permission() 中包装为
      StorageError，同样退出码 1，原有授权与表结构不变。

5. 查询只读与缺失文件初始化
   - check 等查询只执行 SELECT，不修改授权记录；
   - 但任何成功走到 store.connect() 的调用（含查询）在文件缺失且父
     目录可写时，都会创建 rules.db 并初始化空的 role_permissions 表；
   - 第 3 步失败（invalid_name）不创建文件；第 4 步失败
     （storage_error）不把失败伪装成拒绝：stdout 必为空。
