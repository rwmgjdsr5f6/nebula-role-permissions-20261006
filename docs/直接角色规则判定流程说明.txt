一、公开入口与整体流程
----------------------
唯一公开入口是命令行：

    python -m rbac --db FILE grant ROLE PERMISSION
    python -m rbac --db FILE check MEMBER PERMISSION

（核对位置：rbac/__main__.py 的 _build_parser() 与 main()。）

一次调用从输入到输出的完整路径：

1. 命令行输入
   argparse 解析 --db 路径与子命令参数（grant 接收 role、permission；
   check 接收 member、permission）。
   核对位置：rbac/__main__.py _build_parser()、main() 开头。

2. 名称规整
   两个名称参数先经 policy.normalize_name() 处理：去除首尾空白后按完整
   字符串大小写敏感匹配；去除空白后为空则返回 None。main() 发现任一
   名称为 None 即输出 invalid_name 并以退出码 2 结束，此分支不打开
   数据库、不改动任何已有授权。
   核对位置：rbac/policy.py normalize_name()；rbac/__main__.py main()
   中 normalized 校验段。

3. 数据库准备
   名称全部有效后，store.connect(db_path) 打开（必要时创建）SQLite
   规则文件，并执行 CREATE TABLE IF NOT EXISTS 确保 role_permissions
   表（主键 (role, permission)）就绪。任何 sqlite3 层面的失败统一
   包装为 StorageError，由 main() 输出 storage_error 并以退出码 1
   结束。
   核对位置：rbac/store.py connect()、_SCHEMA、StorageError；
   rbac/__main__.py main() 中 try/except store.StorageError 段。

4. 直接角色匹配
   - grant：store.grant_permission() 先按规整后的（角色, 权限）组合做
     精确查询：组合已存在时按幂等成功直接返回；组合不存在时执行普通
     INSERT 并提交，再复查该组合确实可被读出。规则已存在时不产生重复
     行；既有表的唯一约束或检查约束阻止新增时，普通 INSERT 抛出的
     sqlite3 失败统一包装为 StorageError（不再用 INSERT OR IGNORE 吞掉
     约束拒绝）。
   - check：policy.roles_for(member) 从固定配置 FIXED_MEMBER_ROLES
     取出成员的直接角色列表（当前仅 alice -> ("reader",)，未配置成员
     得到空列表），store.permission_granted() 只读查询这些角色中是否
     有任一直接拥有请求权限。
   核对位置：rbac/store.py grant_permission()、permission_granted()；
   rbac/policy.py FIXED_MEMBER_ROLES、roles_for()。

5. 决定输出
   check 由 policy.decide() 生成决定：
   - 成员无直接角色 -> allowed=false，reason="成员未配置"；
   - 有角色且规则命中 -> allowed=true，reason="直接角色授权"；
   - 有角色但规则未命中 -> allowed=false，reason="权限未授予"。
   结果以紧凑分隔符的 JSON 写入标准输出并追加一个换行。
   核对位置：rbac/policy.py decide() 及 REASON_* 常量；
   rbac/__main__.py _emit()、_fail()。


二、主流程示例（可逐条复现核对）
--------------------------------
前提：父目录已存在、rules.db 尚不存在。以下命令在项目根目录执行。

1) 授予 reader 权限 documents:read：

    python -m rbac --db rules.db grant reader documents:read

   预期：退出码 0；标准错误为空；标准输出恰为单个 JSON 对象加一个换行：

    {"role":"reader","permission":"documents:read"}

   副作用：创建 rules.db 文件与 role_permissions 表，并写入一条
   (reader, documents:read) 记录。

2) 随后查询 alice 是否拥有 documents:read：

    python -m rbac --db rules.db check alice documents:read

   预期：退出码 0；标准错误为空；标准输出恰为单个 JSON 对象加一个换行：

    {"member":"alice","permission":"documents:read","roles":["reader"],"allowed":true,"reason":"直接角色授权"}

   即允许 alice，其角色为 reader，原因是直接角色授权。

3) 同库查询未授予的权限 documents:write：

    python -m rbac --db rules.db check alice documents:write

   预期输出（退出码 0，标准错误为空）：

    {"member":"alice","permission":"documents:write","roles":["reader"],"allowed":false,"reason":"权限未授予"}

   alice 有角色 reader，但规则库中没有 (reader, documents:write)，
   故 allowed 为 false，原因为权限未授予。

4) 同库查询未配置成员 bob：

    python -m rbac --db rules.db check bob documents:read

   预期输出（退出码 0，标准错误为空）：

    {"member":"bob","permission":"documents:read","roles":[],"allowed":false,"reason":"成员未配置"}

   bob 不在固定配置中，角色列表为空，allowed 为 false，原因为成员未配置。

5) 持久化与幂等：
   - 每次调用都重新打开同一数据库文件；重新打开 rules.db 后再次执行
     第 2 步的 check，输出与之前完全一致，授权记录仍然保留。
   - 重复执行第 1 步的 grant，因规整后的 (role, permission) 组合已存在、
     写入前的精确查询即按幂等成功处理，role_permissions 表中仍只有一条
     (reader, documents:read) 记录，不增加规则记录。


三、名称与存储边界（逐条可核对）
--------------------------------
1. 名称规整与大小写
   名称先去除首尾空白，再按完整字符串大小写敏感匹配。例如带首尾空白
   的 "  reader\t" 规整为 "reader" 后参与授权与查询；而 "Alice" 不会
   命中固定成员 "alice"（按未配置成员处理），"documents:Read" 不会
   命中已授予的 "documents:read"（按权限未授予处理）。
   核对位置：rbac/policy.py normalize_name()；tests 中
   test_surrounding_whitespace_is_trimmed、test_name_matching_is_case_sensitive。

2. 空名称 / 纯空白名称
   任一名称去除首尾空白后为空（空字符串或纯空白）时：
   - 退出码 2；
   - 标准输出为空；
   - 标准错误恰为一行 {"error":"invalid_name"} 加一个换行；
   - 不打开、不创建数据库文件，也不改动任何已有授权。
   核对位置：rbac/__main__.py main() 中 normalized 校验段（注释明确
   "不打开存储、不改动任何已有授权"）；tests 中
   test_empty_or_blank_names_are_invalid_and_create_no_database、
   test_invalid_name_does_not_change_existing_grants。

3. 数据库父目录不存在
   名称有效但 --db 路径的父目录不存在（sqlite3 无法创建文件）时：
   - 退出码 1；
   - 标准输出为空；
   - 标准错误恰为一行 {"error":"storage_error"} 加一个换行。
   核对位置：rbac/store.py connect() 将 sqlite3.Error 包装为
   StorageError；rbac/__main__.py main() 的 except 分支；tests 中
   test_missing_parent_directory_is_storage_error。

4. 名称与路径同时无效
   名称为空且数据库父目录也不存在时，优先报名称错误：退出码 2，
   标准错误为 {"error":"invalid_name"}，因为名称校验发生在打开
   数据库之前。
   核对位置：rbac/__main__.py main() 中名称校验先于 store.connect()
   的执行顺序；tests 中 test_invalid_name_takes_precedence_over_storage_error。

5. 既有表约束阻止 grant 写入
   规则文件中的 role_permissions 可能带与标准结构（复合主键）不同的
   既有约束，例如 role TEXT NOT NULL UNIQUE 的单列唯一约束，或
   permission 列上的 CHECK(permission <> 'documents:write') 检查约束。
   grant 的幂等性只看规整后的（角色, 权限）组合是否已存在：
   - 组合已存在：按幂等成功处理，退出码 0，返回现有 role、permission
     JSON，标准错误为空，不增加记录；
   - 组合不存在但被唯一约束或检查约束阻止新增：退出码 1，标准输出为空，
     标准错误恰为一行 {"error":"storage_error"} 加一个换行；原有授权、
     其他表与既有表结构保持不变。
   修复前 grant 用 INSERT OR IGNORE，会把约束拒绝一并吞掉而在规则并未
   写入时仍报告成功；现改为写入前精确查询 + 普通 INSERT + 提交后复查，
   只有目标规则实际持久保存才算成功。
   核对位置：rbac/store.py grant_permission()；tests/test_grant_constraint.py。

6. 固定成员关系与数据边界
   - alice 与 reader 的对应关系来自 rbac/policy.py 中的固定配置
     FIXED_MEMBER_ROLES，不来自数据库；数据库只保存"角色 -> 权限"
     规则（rbac/store.py 模块 docstring 明确说明成员-角色对应不入库）。
   - grant 只写入角色-权限规则，不改变任何成员的角色配置。
   - check 是只读判定，不改变已有授权记录（tests 中
     test_check_is_read_only 核对查询前后授权记录一致）；但 check 同样
     会经 store.connect() 打开规则库，因此在数据库文件尚不存在时，
     一次 check 也可能创建该文件并建立表结构。
   - 不存在登录、角色继承或成员管理功能（rbac/policy.py 注释），本文
     不将这些长期规划方向描述为已实现能力。
