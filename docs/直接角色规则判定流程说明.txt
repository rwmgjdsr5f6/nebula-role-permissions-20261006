一、处理路径总览（从命令行输入到决定输出）
------------------------------------------
每次调用都是一次独立进程：解析参数 → 规整名称 → 打开数据库 → 执行
授权或判定 → 输出单行 JSON → 按约定退出码结束。各环节与源码核对位置：

1. 命令行输入
   入口为 `python -m rbac`，参数解析在 rbac/__main__.py 的
   _build_parser()：--db 指定 SQLite 规则文件路径（必填），子命令
   grant 接收 ROLE PERMISSION，子命令 check 接收 MEMBER PERMISSION。
   main()（rbac/__main__.py:51）先把标准输出/标准错误重配为 UTF-8，
   再解析参数。

2. 名称规整
   main() 对两个名称参数逐一调用 policy.normalize_name()
   （rbac/policy.py:16）：先去除首尾空白（str.strip()），再按完整
   字符串大小写敏感使用；去空白后为空的名称得到 None。任一名称为
   None 时，main() 直接输出 {"error":"invalid_name"} 并以退出码 2
   结束，此时尚未打开数据库（详见第四节）。

3. 数据库准备
   名称全部有效后，main() 调用 store.connect(args.db)
   （rbac/store.py:22）：用 sqlite3.connect 打开（必要时创建）规则
   文件，并执行建表语句（rbac/store.py 的 _SCHEMA，CREATE TABLE IF
   NOT EXISTS role_permissions，主键为 (role, permission)）确保表
   结构就绪。任何 sqlite3 层面的失败统一包装为 store.StorageError，
   由 main() 捕获后输出 {"error":"storage_error"} 并以退出码 1 结束。

4. 直接角色匹配
   - grant 分支：main() 调用 store.grant_permission()
     （rbac/store.py:40），以 INSERT OR IGNORE 把（角色, 权限）写入
     role_permissions 表并提交；规则已存在时不产生重复行。
   - check 分支：main() 先调用 policy.roles_for()（rbac/policy.py:27）
     从固定配置 FIXED_MEMBER_ROLES（rbac/policy.py:11）取成员的直接
     角色列表（当前仅 alice -> ("reader",)，其余成员为空列表），再
     调用 store.permission_granted()（rbac/store.py:52）做只读查询：
     角色列表为空时直接返回 False，否则查 role_permissions 表中是否
     存在"任一直接角色拥有该权限"的记录。

5. 决定输出
   check 分支由 policy.decide()（rbac/policy.py:33）生成决定：
   成员无直接角色 → allowed=False，原因为"成员未配置"；
   有角色且规则命中 → allowed=True，原因为"直接角色授权"；
   有角色但规则未命中 → allowed=False,原因为"权限未授予"。
   三种原因文案即 rbac/policy.py 第 4–6 行的常量。
   输出由 rbac/__main__.py 的 _emit()/_fail() 完成：成功时标准输出
   为单个紧凑 JSON 对象（分隔符为 (",", ":")，键内无空格）加一个
   换行，标准错误为空，退出码 0；失败时标准输出为空，标准错误仅为
   一个紧凑 JSON 错误对象加换行。


二、主流程示例（grant 后 check，含完整预期输出）
------------------------------------------------
前提：当前工作目录已存在，且其中尚不存在 rules.db 文件。以下命令在
仓库根目录执行（rbac 包可被 Python 找到）。

第一步，授予角色权限：

    python -m rbac --db rules.db grant reader documents:read

预期：退出码 0；标准错误为空；标准输出恰为以下一行（单个 JSON 对象
加一个换行）：

    {"role":"reader","permission":"documents:read"}

副作用：创建 rules.db 文件并建立 role_permissions 表，写入一条规则
记录 ("reader", "documents:read")。grant 只保存"角色 -> 权限"规则，
不改变任何成员的角色（成员角色是固定配置，见第五节）。

第二步，查询成员权限：

    python -m rbac --db rules.db check alice documents:read

预期：退出码 0；标准错误为空；标准输出恰为以下一行：

    {"member":"alice","permission":"documents:read","roles":["reader"],"allowed":true,"reason":"直接角色授权"}

即允许 alice，其直接角色为 reader，允许原因是直接角色授权。该 JSON
与 policy.decide() 返回字典的键序一致（member、permission、roles、
allowed、reason），由 json.dumps 紧凑序列化。

以上两行预期输出均已在本仓库源码上实际运行核对，与
tests/test_direct_role_flow.py 中
test_grant_then_check_allowed_persisted_and_idempotent 的断言一致。


三、判定分支与持久化行为
------------------------
以下均接续第二节的同一 rules.db（已授予 reader documents:read）：

1. 查询未授予的权限：

       python -m rbac --db rules.db check alice documents:write

   退出码 0，标准错误为空，标准输出为：

       {"member":"alice","permission":"documents:write","roles":["reader"],"allowed":false,"reason":"权限未授予"}

   alice 有角色 reader，但规则库中没有 (reader, documents:write)，
   故 allowed 为 false，原因为权限未授予。

2. 查询未配置成员：

       python -m rbac --db rules.db check bob documents:read

   退出码 0，标准错误为空，标准输出为：

       {"member":"bob","permission":"documents:read","roles":[],"allowed":false,"reason":"成员未配置"}

   bob 不在 FIXED_MEMBER_ROLES 中，角色列表为空，allowed 为 false，
   原因为成员未配置；此时 store.permission_granted() 不执行 SQL
   查询直接返回 False（rbac/store.py:54-55）。

3. 重新打开同一数据库仍保留授权：每次调用都是新进程、重新
   sqlite3.connect 同一文件；授权已提交持久化，再次执行第二节的
   check alice documents:read 结果与首次完全相同。

4. 重复授予不增加规则记录：再次执行
   `python -m rbac --db rules.db grant reader documents:read`，
   因 INSERT OR IGNORE 与 (role, permission) 主键约束，表中仍只有
   一条 ("reader", "documents:read") 记录，输出与退出码不变。

5. 空规则库查询：若跳过 grant 直接在新库上 check alice
   documents:read，退出码 0，输出中 allowed 为 false、原因为
   权限未授予（角色存在但无匹配规则）。


四、名称与存储的边界行为
------------------------
1. 名称规整规则：所有角色名、权限名、成员名先去除首尾空白，再按
   完整字符串大小写敏感匹配（policy.normalize_name()，rbac/policy.py:16）。
   例如 "  reader\t" 规整为 "reader" 后入库；而 "Alice" 不等于
   "alice"（按未配置成员处理），"documents:Read" 不等于
   "documents:read"（按权限未授予处理）。

2. 空名称 / 纯空白名称：任一名称参数去空白后为空（空字符串或纯
   空白）时，退出码 2，标准输出为空，标准错误仅为一行：

       {"error":"invalid_name"}

   此时不打开、不创建数据库文件，也不改动任何已有授权——名称校验
   在 store.connect() 之前完成（rbac/__main__.py:65-69）。

3. 存储失败：名称有效但数据库无法打开（典型情形：--db 指向的父目录
   不存在）时，退出码 1，标准输出为空，标准错误仅为一行：

       {"error":"storage_error"}

   sqlite3 层面的打开与读写失败统一由 store.StorageError 包装，
   由 main() 捕获后走同一输出路径。

4. 错误优先级：名称与路径同时无效（如父目录不存在且名称为空白）时，
   优先报名称错误——退出码 2、标准错误为 {"error":"invalid_name"}，
   因为名称校验先于数据库打开。

以上边界行为与 tests/test_direct_role_flow.py 中
test_empty_or_blank_names_are_invalid_and_create_no_database、
test_missing_parent_directory_is_storage_error、
test_invalid_name_takes_precedence_over_storage_error 等用例一一对应。


五、固定配置与存储边界
----------------------
1. alice 的 reader 关系来自固定配置而非数据库：成员到直接角色的对应
   写在 rbac/policy.py 的 FIXED_MEMBER_ROLES（当前仅 alice ->
   ("reader",)），不入库、不可通过命令行管理；不存在成员管理、角色
   继承或登录等入口。

2. grant 不改变成员角色：grant 只向 role_permissions 表写入
   "角色 -> 权限"规则，没有任何命令能修改 FIXED_MEMBER_ROLES。

3. check 不改变已有授权记录：check 路径对数据库只执行只读 SELECT
   （store.permission_granted()），查询前后 role_permissions 表内容
   不变（回归测试 test_check_is_read_only 直接核对表中记录）。

4. 但打开规则库仍可能创建文件、建立表结构：store.connect() 在名称
   校验通过后总会执行——数据库文件不存在时由 sqlite3 创建，并通过
   CREATE TABLE IF NOT EXISTS 确保 role_permissions 表存在。因此
   即使是一次"只读"的 check，也可能在磁盘上新建空的规则库文件；
   数据库中只保存"角色 -> 权限"这一类规则，不保存成员-角色关系。

5. 数据库表结构（rbac/store.py 的 _SCHEMA）：

       CREATE TABLE IF NOT EXISTS role_permissions (
           role       TEXT NOT NULL,
           permission TEXT NOT NULL,
           PRIMARY KEY (role, permission)
       )
