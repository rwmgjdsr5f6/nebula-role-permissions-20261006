一、公开入口与实际顺序
----------------------
本文涉及的两个公开入口（其余子命令见文末“其他公开入口”）：

    python -m rbac --db FILE grant ROLE PERMISSION
    python -m rbac --db FILE check MEMBER PERMISSION

核对位置：rbac/__main__.py 的 _build_parser()（参数定义）与 main()
（执行顺序）。

一次调用从输入到输出严格按以下顺序进行：

1. 名称规整
   argparse 取出原始参数后，main() 对各名称参数逐个调用
   policy.normalize_name()：先 name.strip() 去除首尾空白，再按完整
   字符串大小写敏感地区分名称；去空白后为空字符串则返回 None。
   任一名称为 None 时，main() 立即经 _fail("invalid_name") 输出错误并
   返回退出码 2，此分支发生在 store.connect() 之前，不打开也不创建
   数据库文件。
   核对位置：rbac/policy.py normalize_name()；rbac/__main__.py
   main() 中 normalized 列表构造与 any(name is None ...) 校验段。

2. 数据库准备
   名称全部有效后，main() 调用 store.connect(db_path)：sqlite3 打开
   （必要时创建）规则文件，并执行 _SCHEMA 中的
   CREATE TABLE IF NOT EXISTS role_permissions(...)（复合主键
   (role, permission)）后提交。打开或建表初始化阶段的任何
   sqlite3.Error 都在 connect() 内包装为 StorageError，由 main()
   经 _fail("storage_error") 输出并返回退出码 1。
   核对位置：rbac/store.py connect()、_SCHEMA、StorageError；
   rbac/__main__.py main() 中连接处的 try/except store.StorageError。

3. 固定角色读取
   对 check，main() 调用 policy.roles_for(member)：成员角色只来自源码
   内的固定配置 FIXED_MEMBER_ROLES（当前仅 "alice": ("reader",)），
   配置中不存在的成员得到空列表。该对应关系不入库，grant 与任何其他
   命令都无法修改它；数据库中只保存“角色 -> 权限”这一类规则
   （rbac/store.py 模块 docstring 与 rbac/policy.py FIXED_MEMBER_ROLES
   上方注释均明确这一边界）。
   核对位置：rbac/policy.py FIXED_MEMBER_ROLES、roles_for()。

4. 直接授权匹配
   - grant 走 store.grant_permission()：先按规整后的（角色, 权限）
     组合精确查询，组合已存在即按幂等成功返回；不存在则执行普通
     INSERT、提交并复查该组合确实可读出，任何 sqlite3 失败统一包装
     为 StorageError。
   - check 走 store.permission_granted(conn, roles, permission)：
     roles 为空时直接返回 False，不向规则表发出任何 SQL；roles 非空
     时执行只读 SELECT，判定这些角色中是否有任一行的 permission 与
     请求权限精确相等（大小写敏感，"*"、"%" 等均为普通字符）。
   核对位置：rbac/store.py grant_permission()、permission_granted()；
   rbac/__main__.py main() 中 check 分支
   （permission_granted(conn, policy.roles_for(...), permission)）。

5. 结果输出
   main() 将上一步的匹配布尔值交给 policy.decide(member, permission,
   granted)，由它再次读取固定角色并选择结论：
   - 角色列表为空            -> allowed=false，reason="成员未配置"；
   - 有角色且匹配命中        -> allowed=true， reason="直接角色授权"；
   - 有角色但无任何匹配行    -> allowed=false，reason="权限未授予"。
   结果对象经 _emit() 写到标准输出：json.dumps 使用紧凑分隔符
   (",", ":")、ensure_ascii=False（中文原因原样输出），末尾恰好追加
   一个换行；main() 开头还将 stdout/stderr 重配置为 UTF-8，保证任何
   区域配置下中文原因按 UTF-8 输出。
   核对位置：rbac/policy.py decide() 及三个 REASON_* 常量；
   rbac/__main__.py _emit()、_fail() 与 main() 开头的 reconfigure 段。


二、主流程样例（按源码可核对的预期）
------------------------------------
共同前提：父目录（当前工作目录）已存在且可写，rules.db 尚不存在。
以下命令在仓库根目录执行；每一步成功调用均为：退出码 0，标准错误
为空，标准输出恰为一行 UTF-8 JSON 加一个换行。

1) 授予 reader 角色 documents:read 权限：

    python -m rbac --db rules.db grant reader documents:read

   预期标准输出（末尾一个换行）：

    {"role":"reader","permission":"documents:read"}

   预期副作用：rules.db 被创建，role_permissions 表就绪，并写入一条
   (reader, documents:read) 记录。重复执行同一 grant 为幂等：
   grant_permission() 的写入前精确查询命中既有组合即成功返回，
   表中始终只有这一条记录。

2) 查询 alice 是否拥有 documents:read：

    python -m rbac --db rules.db check alice documents:read

   预期标准输出（末尾一个换行）：

    {"member":"alice","permission":"documents:read","roles":["reader"],"allowed":true,"reason":"直接角色授权"}

   即 alice 的角色为 ["reader"]，allowed 为 true，原因是“直接角色
   授权”：固定角色 reader 已在库中获授该权限。

3) 同一库查询未授予的 documents:write：

    python -m rbac --db rules.db check alice documents:write

   预期标准输出（末尾一个换行）：

    {"member":"alice","permission":"documents:write","roles":["reader"],"allowed":false,"reason":"权限未授予"}

   alice 有角色 reader，但 role_permissions 中不存在
   (reader, documents:write)，故 allowed 为 false，原因为“权限未
   授予”。这是正常业务拒绝，不是执行失败：退出码仍为 0。

4) 同一库查询固定配置中不存在的 bob：

    python -m rbac --db rules.db check bob documents:read

   预期标准输出（末尾一个换行）：

    {"member":"bob","permission":"documents:read","roles":[],"allowed":false,"reason":"成员未配置"}

   bob 的 roles 为空，allowed 为 false，原因为“成员未配置”，同样以
   退出码 0 结束。由于 permission_granted() 对空角色列表直接返回
   False，该判定不查询规则表（此性质在第三节存储边界中同样关键）。


三、正常拒绝与执行失败的区分（逐条可核对）
------------------------------------------
两类失败互斥，优先级固定：名称校验先于一切存储访问；存储访问先于
业务结论。

1. 名称规整规则（正常匹配语义，非错误）
   名称只做首尾空白裁剪，不做大小写折叠：随后按完整字符串大小写
   敏感匹配。例如 "  reader\t" 规整为 "reader"；"Alice" 不会命中
   固定成员 "alice"（按“成员未配置”处理），"documents:Read" 不会
   命中已授予的 "documents:read"（按“权限未授予”处理）。输出 JSON
   中的名称一律为规整后的值。
   核对位置：rbac/policy.py normalize_name()。

2. 名称无效：退出码 2（invalid_name）
   任一名称经 strip() 后为空（空字符串或纯空白）时：
   - 退出码 2；
   - 标准输出为空；
   - 标准错误恰为一行 {"error":"invalid_name"} 加一个换行；
   - 不打开、不创建数据库文件，不改动任何已有授权。
   即使同时给出父目录不存在的 --db 路径，仍以退出码 2 为准，因为
   名称校验在 main() 中先于 store.connect()。
   核对位置：rbac/__main__.py main() 中 normalized 校验段（注释
   “不打开存储、不改动任何已有授权”）与 _fail()。

3. 存储失败：退出码 1（storage_error）
   名称有效，但存储无法完成打开、初始化或业务读写时：
   - 退出码 1；
   - 标准输出为空（不得夹带任何正常业务 JSON）；
   - 标准错误恰为一行 {"error":"storage_error"} 加一个换行，
     不附加错误详情或异常堆栈。
   以下三种输入均落入这一协议，且失败发生阶段不同：

   a. 父目录不存在
      --db 所在目录不存在，规则文件无法创建：打开/初始化失败，
      connect() 包装为 StorageError。grant 与 check 同样适用。
      核对位置：rbac/store.py connect()；rbac/__main__.py main()
      连接处 except 分支。

   b. 文件存在但内容不是 SQLite 数据库
      sqlite3 可以建立连接，但 connect() 内的 CREATE TABLE
      IF NOT EXISTS 建表初始化必然失败并包装为 StorageError。该失败
      发生在任何业务分支之前：即使查询的是 bob（空角色，本可不查
      规则表），也先得到退出码 1 的 storage_error，而不是“成员未
      配置”。文件原有字节不被清空、覆盖或修补。
      核对位置：rbac/store.py connect() 中 _SCHEMA 执行段；
      tests/test_non_sqlite_rulefile.py 对该边界的固化。

   c. 规则表缺少业务所需的 permission 列，但初始化可以完成
      当 role_permissions 表已存在但结构不兼容（例如只有 role 列、
      缺少 permission 列）时，CREATE TABLE IF NOT EXISTS 对既有表是
      空操作，connect() 正常返回；随后：
      - 查询 alice（角色 ["reader"] 非空）必须读取 permission 列，
        permission_granted() 的 SELECT 触发 sqlite3 错误并包装为
        StorageError：退出码 1，stdout 为空，stderr 仅为
        {"error":"storage_error"} 加换行，不得退化为 allowed=true
        或 false 的正常判定；
      - 查询 bob 时 roles_for("bob") 返回空列表，
        permission_granted() 在执行任何 SQL 前即返回 False，缺列
        不影响该路径：仍退出码 0，输出与第二节第 4 步完全相同的
        “成员未配置”结果。
      即“缺权限列但初始化可完成”时 bob 正常返回；而“非 SQLite
      文件”的初始化失败先于连接返回，bob 也只能得到 storage_error。
      核对位置：rbac/store.py permission_granted() 开头
      `if not roles: return False` 与其中的 except sqlite3.Error；
      tests/test_incompatible_schema.py 对两种成员结果的固化。

4. 查询只读与缺文件初始化
   - check 是只读判定：permission_granted() 只执行 SELECT，不修改
     任何授权记录。
   - 但 check 与 grant 一样必经 store.connect()：当规则文件尚不存在
     而父目录存在且可写时，首次调用（包括查询）会创建空规则文件并
     建立 role_permissions 空表。“查询不改数据”与“缺文件时初始化
     空库”两件事并存：初始化只建库建表，不写入任何授权规则。
   核对位置：rbac/store.py connect()、permission_granted()。
